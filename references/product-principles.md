# MinimalShip product principles

These are original MinimalShip working principles. They are filters for product decisions, not a startup curriculum and not investment advice.

## Start from a real need

Name the user, the painful situation, the current workaround, and the behavior that proves the problem matters now. A broad audience with mild interest is weaker evidence than a narrow group that will try a rough first version.

## Build a complete small path

Prefer one useful journey from input to result over a catalogue of disconnected screens. A first release can be narrow, manual behind the scenes, or visually plain when it creates real value and the boundary is honest.

## Learn with the first users

Observe the first users directly. Help them complete the task, notice where the model is wrong, and record what they do rather than only what they say. Manual support is acceptable when it is transparent and teaches what to automate next.

## Choose one cycle goal

Each cycle has one primary outcome and one leading measure. Maintenance, bugs, experiments, and nice-to-have ideas may be listed, but they cannot obscure the goal or consume the verification time reserved for it.

## Evidence before ceremony

A spec, agent, diagram, or launch plan is useful only when it changes a decision or makes behavior easier to verify. Do not imitate the shape of a mature company before the product needs it.

## Protect the core path

Fast delivery never excuses unsafe data handling, missing error behavior, untested migrations, or unresolved release blockers. Scope can shrink; acceptance and honesty cannot.

## Improve by observed outcomes

After shipping, compare the intended outcome with real usage, feedback, errors, and support cost. Improve, remove, or expand based on evidence. Do not preserve a feature because it took effort to build.
